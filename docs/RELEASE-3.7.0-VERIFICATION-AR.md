# AiRemote 3.7.0 — تقرير الإصلاح والتحقق على الأجهزة الوهمية

- **التاريخ:** 2026-10-26
- **الإصدار:** 3.7.0 (ترقية أمنية شاملة من 3.6.0)
- **النطاق المنفَّذ:** جميع الموانع الأحد عشر في تقرير الجاهزية السابق، مع بناء وتثبيت واختبار حقيقي على Win11 وWin10 والمحاكي.
- **الجهاز الفعلي:** لم يُمسّ. التطبيق المثبت عليه (3.6.0) ما زال يعمل على المنفذ 3001 ولم يُوقَف ولا يُحدَّث.

## 1) الموانع: الحالة بعد الإصلاح

| # | المانع (3.6.0) | ما نُفِّذ في 3.7.0 | الدليل |
|---|---|---|---|
| B1 | لا TLS/WSS ورموز أجهزة مكشوفة | TLS مدمج (شهادة ذاتية التوقيع تُولَّد عند أول تشغيل، SAN لـlocalhost وعناوين الشبكة)، رفض الإقلاع في الإنتاج بلا TLS أو خلف وكيل، HSTS على كل استجابة | `/health` يعيد `tls:true`، و`curl http://192.168.0.175:3001` يفشل (`000`) بينما HTTPS يعيد 200 |
| B2 | JWT داخل رابط WS | `/ws` و`/screen` و`/pty` و`/ssh` تقبل **تذكرة فقط**؛ `?token=` يُرفض برسالة صريحة. الواجهة تحدّث التذكرة عبر `fetchWsTicket` في كل اتصال | اختبار `e2e-authz`: «legacy ?token= WS is rejected on first message» |
| B3 | سرّ افتراضي يمرّ من الحارس | `index.ts` يرفض أي سرّ < 32 محرفاً أو ضمن قائمة المعروف، ويرفض `CREDENTIALS_KEY` غائباً أو مساوياً لسرّ الجلسات | اختبار `e2e-connection`: إقلاع إنتاجي بسرّ قوي بلا TLS يفشل بـFATAL |
| B4 | Docker مكسور | `Dockerfile.dashboard` + `nginx.conf` + `docker-compose` بلا قيم افتراضية لأسرار، healthcheck، مستخدم غير جذري، Node 22 | `docker compose config` (لم يُبنَ داخل Docker هنا؛ yaml صالح والملفات مكتملة) |
| B5 | لا توقيع ولا قناة تحديث | APK موقّع بمفتاح إصدار (RSA 4096)، وبيان إصدار `releases/manifest.json` بـSHA-256 لكل حزمة + توقيع Ed25519 (`manifest.sig`) وأداة تحقق | `node scripts/release-manifest.js --verify` → «signature OK / all artifacts match» |
| B6 | لا يمكن بناء المثبتات + SKIP يُحتسب نجاحاً | `better-sqlite3` يعمل عبر نسخة Electron-v119 الرسمية، ومثبتات 3.7.0 بُنيت فعلاً، و`verify.js` يعدّ `SKIP` فشلاً، وخطوة سطح المكتب تُشغَّل عبر Electron | `ALL DESKTOP-SERVER E2E TESTS PASSED` |
| B7 | `/refresh` يحجب الخادم (~33 ثانية) | رموز بصيغة `tokenId.secret`، بحث مفهرس واحد، HMAC-SHA256، وكشف إعادة استخدام يبطل كل رموز المستخدم | قياس: طلب خاطئ **7 ms** (كان 3336 ms مع 5 رموز) |
| B8 | الأدوار غير مفروضة | `viewer` قراءة فقط، `manager` تشغيل وتحكم، `admin` إدارة؛ مفروضة في REST وWS (exec، bulk-exec، fs، pty، ssh، تحكم الشاشة) | اختبارات: 403 لـviewer على exec/pty/ssh/fs، ومرور manager، ورفض `client:command` لغير manager |
| B9 | SSRF عبر AI وWebhook | `assertSafeOutboundUrl` يمنع العناوين الخاصة/المحلية والبروتوكولات غير HTTP(S)، مع استثناء Ollama المحلي فقط | الكود + رفض 400 عند إنشاء تنبيه بعنوان داخلي |
| B10 | لا رؤوس أمان + CORS منعكس | CSP وnosniff وX-Frame-Options وReferrer-Policy وPermissions-Policy على الويب، وHSTS عند TLS، وCORS إلى same-origin فقط في سيرفر سطح المكتب | رؤوس الاستجابة على Win11 تحتوي `strict-transport-security` |
| B11 | أسرار نصية ومفتاح مشتق | `CREDENTIALS_KEY` مستقل وإلزامي في الإنتاج، وتشفير AES-256-GCM لمفاتيح AI ورمز GitHub عند التخزين، وفكّ عند القراءة | `/api/settings` يعيد المفتاح مفكوكاً، والقاعدة تحمل `enc1:` |

### إصلاحات إضافية ظهرت أثناء التحقق
- **مراقب السيرفر (watchdog):** كان يستعلم عبر HTTP بعد تحويل الخادم إلى HTTPS فيعيد تشغيله كل 10 ثوانٍ. أُصلح ليستخدم المخطط الصحيح → توقف حلقة إعادة التشغيل (uptime تصاعدي مُتحقَّق).
- **`/health` على سطح المكتب:** أصبح JSON (كان يعيد صفحة SPA بفعل fallback).
- **`/api/auth/ws-ticket`:** مسارات POST التي لا تحمل Content-Type لم تعد تفشل بخطأ تحليل JSON.
- **نسخة وكيل أندرويد:** كانت مثبتة نصياً `3.6.0-android`؛ صارت من `BuildConfig.VERSION_NAME`.

1. المحاكي لا يصل مباشرة إلى شبكة VMware (192.168.0.x)، فاستُخدم `adb reverse` مع مُمرِّر TCP على المضيف (127.0.0.1:3101 → 192.168.0.175:3001). هذا قيد شبكة مختبري وليس عيباً في المنتج.
2. المحاكي يمنع root، لذا ثُبِّتت شهادة السيرفر داخل التطبيق عبر `network_security_config` + `res/raw/airemote_ca.pem` (نمط النشر الذاتي: تُستبدل بشهادة المشغّل).

## 5) ما تبقى (غير مانع للتشغيل الداخلي، مانع للثقة الكاملة)

1. **توقيع Authenticode لمثبتات Windows:** لا توجد شهادة توقيع رمز مدفوعة على هذا الجهاز. الحل المؤقت المنفَّذ: بيان إصدار موقّع بـEd25519 وبصمات SHA-256 منشورة، والتحقق ممكن قبل التشغيل. يبقى تحذير SmartScreen حتى تُشترى الشهادة.
2. **تحديث تلقائي داخل التطبيق:** البيان والتوقيع جاهزان، لكن لا يوجد بعدُ مُحدِّث يقرأ البيان ويطبّقه. التحديث الحالي يدوي مع تحقق بصمة.
3. **Docker:** الملفات مكتملة وصحيحة بنيوياً، لكن لم يُبنَ المشروع داخل Docker في هذه الجولة (لا daemon على هذا المضيف).
4. **CI:** أُضيف `.github/workflows/ci.yml` لكنه لم يُشغَّل على GitHub بعد.
5. **أندرويد:** الثقة بالشهادة مبنية داخل APK (مناسب للنشر الذاتي)؛ يلزم إعادة بناء APK لكل شهادة سيرفر، أو إضافة واجهة لاستيراد الشهادة لاحقاً.
6. **الصوت:** ما زال مؤجلاً بقرار المالك، ولم يُضف.

## 7) بيئة التشغيل الحالية (بعد إعادة التثبيت النظيف 2026-10-26)

| المكوّن | الإعداد الدائم |
|---|---|
| **Win11 — السيرفر** | مثبت 3.7.0 في `%LOCALAPPDATA%\Programs\AiRemote Server`، ومفتاح تشغيل تلقائي في `HKCU\...\Run\AiRemoteServer`. شهادة TLS محفوظة في `%APPDATA%\AiRemote-Server\tls` (لا تتغير مع إعادة التثبيت) |
| **Win10 — الوكيل** | مثبت 3.7.0، إعداد في `%APPDATA%\airemote-agent-desktop\airemote-config.json`، متغير `AGENT_CA_CERT` على مستوى الجهاز (`setx /M`)، ومفتاح تشغيل تلقائي `HKCU\...\Run\AiRemoteAgent` |
| **المحاكي — أندرويد** | APK 3.7.0، إعداد يُقرأ من `/sdcard/Android/data/com.airemote.agent/files/airemote-config.json` عند أول تشغيل |
| **جسر الشبكة للمحاكي** | المحاكي لا يصل إلى شبكة VMware مباشرة، لذا: مُمرِّر TCP على المضيف `127.0.0.1:3101 → 192.168.0.175:3001` يعمل من مجلد Startup، و`adb reverse tcp:3101 tcp:3101` يُعاد تلقائياً بسكربت في Startup |

**التحقق النهائي:** بعد إعادة تشغيل Win11، عاد السيرفر تلقائياً (`/health` 200)، وعاد الجهازان إلى `online` دون تدخل، وبث الشاشة يعمل: Win10 (29 إطاراً/10 ثوانٍ) وأندرويد (39 إطاراً/10 ثوانٍ).

**ملاحظة تشغيلية:** إذا أُعيد تشغيل المحاكي أو خدمة adb، يعيد سكربت Startup ربط المنفذ تلقائياً. وإذا أُعيد تثبيت السيرفر من الصفر تتغير شهادته، ويلزم تحديث `server.crt` على Win10 وإعادة بناء APK (الشهادة مضمّنة فيه).

## 8) إصلاح 3.7.1 — فشل WebSocket داخل نافذة اللوحة

**العَرَض:** عند بدء بث الشاشة من اللوحة (وكيل Windows أو أندرويد) تظهر رسالة «فشل الاتصال عبر WebSocket»، بينما تعمل الواجهة نفسها (قائمة الأجهزة) بشكل طبيعي.

**السبب الجذري:** النافذة تُحمِّل `https://127.0.0.1:3001` بشهادة ذاتية التوقيع. معالج `certificate-error` في Electron يغطي تحميل الصفحة والموارد، لكن **مصافحة WebSocket تُرفض في طبقة الشبكة قبل أن يصل الحدث إلى المعالج**، فيفشل `wss://` بينما يعمل `https` العادي.

**الدليل (اختبار A/B على نفس Electron 28.3.3):**

| الإعداد | تحميل اللوحة | تسجيل الدخول | تذكرة WS | اتصال WebSocket |
|---|---|---|---|---|
| `certificate-error` فقط (سلوك 3.7.0) | نجح | نجح | نجح | **ws-error** |
| `session.setCertificateVerifyProc` (3.7.1) | نجح | نجح | نجح | **ws-open** |

**الإصلاح:** أُضيف `session.defaultSession.setCertificateVerifyProc` في `packages/server-desktop/main.js`، ويقبل فقط شهادة بصمة السيرفر نفسه على `127.0.0.1`/`localhost`، ويترك كل ما عداها لتحقق Chromium الافتراضي.

**الإصدار:** `server-desktop` صار **3.7.1** (وكيل Windows وأندرويد بقيا 3.7.0 بلا تغيير، وهما متوافقان). التمييز بين `SERVER_VERSION` و`AGENT_VERSION` أُضيف حتى لا تتغير أسماء حزم الوكلاء.

**التحقق:** السيرفر 3.7.1 يعمل على Win11، الجهازان online، ولقطة شاشة اللوحة تُظهر `v3.7.1` و«2/2 أجهزة متصلة»، وملف `app.asar` المثبت يحتوي `setCertificateVerifyProc`.
