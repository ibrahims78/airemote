# هجرات المخطط — R7 (3.8.30)

## 1) المشكلة

المخطط كان **17 جملة `CREATE TABLE IF NOT EXISTS`** بلا أي رقم إصدار. النتيجة: الترقية
تستطيع **إضافة** جداول فقط، ولا يوجد مسار لتعديل جدول قائم أو **الرجوع** بإصدار.

## 2) القرار

الاعتماد على بدائية SQLite نفسها: **`PRAGMA user_version`**، بلا جدول تتبّع إضافي يمكن أن
يخرج عن التزامن.

| العنصر | القيمة |
|---|---|
| الأساس (baseline) | **1** = مخطط 3.8.x كما هو |
| أحدث إصدار | **2** = فهارس الاستعلام |
| الاعتماد | قاعدة قديمة (`user_version = 0`) تُعتمد عند **1** بلا أي DDL، لأن `initDb` يضمن وجود الجداول |
| الذرّية | كل خطوة داخل معاملة، وتحديث `user_version` معها: انهيار يترك الإصدار القديم أو الجديد، لا خليطاً |
| الرجوع | `down` حقيقي ينفّذ عكس `up` (حذف ما أُنشئ) — لا خطوة بلا رجوع |

## 3) الخطوات الحالية

| الإصدار | الاسم | up | down |
|---|---|---|---|
| 1 | baseline | — (اعتماد) | — |
| 2 | query-indexes | `idx_audit_log_created` · `idx_audit_log_device` · `idx_sessions_device` · `idx_sessions_user` | حذفها |

## 4) التشغيل

- **تلقائياً عند الإقلاع**: `initDb` يعتمد الأساس ثم ينفّذ المعلّق، ويُسجّل كل خطوة.
- **يدوياً**: `node scripts/migrate.cjs --db <path> --status | --up | --down [--once] [--to N]`
  - `--db` **إلزامي**: أداة تُشغَّل بالخطأ على قاعدة الإنتاج أخطر من ألا توجد.
- **API**: `GET /api/desktop/schema` (admin) يعيد `{version, baseline, latest, pendingUp, pendingDown, steps}`.

## 5) الدليل

`e2e-migrations` (14 فحصاً):
- قاعدة جديدة تُقلع على 2 والفهارس الأربعة موجودة؛
- `down` يُزيل الفهارس ويُبقي الصفوف، و`up` يعيدها ويُبقي الصفوف؛
- قاعدة **قديمة** (جداول + صفوف + `user_version = 0`) تُعتمد عند 1 ثم تُرقّى إلى 2 **بلا فقد صفوف**؛
- الأداة تعرض الحالة وترفض العمل بلا `--db`.

## 6) ما تبقّى

| البند | الحالة |
|---|---|
| هجرة كاسرة (تعديل عمود) | لا توجد بعد؛ الآلية جاهزة لها |
| نسخة احتياطية قبل كل هجرة | متاحة الآن عبر `backup-manager`؛ الربط التلقائي مؤجَّل |
| هجرات على وكيل أندرويد/ويندوز | لا تنطبق (لا قاعدة عند الوكلاء) |
