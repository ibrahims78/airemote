# خطة الوصول إلى مستوى Chrome Remote Desktop عبر نفق Cloudflare — مستند مرجعي

**التاريخ:** 2026-11-20 · **المشروع:** AiRemote 3.17.0 · **الحالة:** تخطيط وتحقق — **لم يُنفَّذ أي تغيير على التطبيق**

---

## 1) الملخّص التنفيذي

- **الدومين `sidawin8n.cfd` صالح** ومسجَّل لدى Spaceship، وتاريخ انتهائه الرسمي **2027-10-19** (≈333 يومًا من اليوم).
- **لكنه ليس على Cloudflare** (Name Servers = `launch1/launch2.spaceship.net`)، ولا توجد سجلات A ⇒ لا موقع منشور.
- **DNSSEC مُفعَّل** على الدومين (DS في السجل) — هذه نقطة حرجة عند نقل الـNS إلى Cloudflare.
- **النفق الحالي في التطبيق غير إنتاجي:** `tunnel.js` يشغّل *quick tunnel* على `http://localhost:3001` بينما السيرفر TLS على 3001، والعنوان مؤقت.
- **الترتيب الموصى به:** (أ) نقل الدومين إلى Cloudflare، (ب) نفق مسمّى + قياس بوابة النجاح من شبكة خارجية، (ج) تضمين النفق في التطبيق، (د) مسار TURN/WebRTC لمستوى CRD.
- **مستوى Chrome Remote Desktop لا يتحقق بالنفق وحده:** النفق يحلّ الوصول، أما الوسائط فتحتاج TURN + WebRTC + قناة تحكم.

المصدر: RDAP السجل (`rdap.centralnic.com/cfd/...`) + WHOIS `whois.nic.cfd` — بتاريخ 2026-11-20.

| الحقل | القيمة |
|---|---|
| الاسم | `SIDAWIN8N.CFD` |
| السجل (Registry) | CentralNic (.cfd) · Handle `D608897100-CNIC` |
| المسجِّل | **Spaceship, Inc.** (IANA 3862) |
| تاريخ التسجيل | **2025-10-19** |

| الحالة | `clientTransferProhibited` · `autoRenewPeriod` |

| DNSSEC | **مُفعَّل** (DS: keyTag 17751 · alg 13 · digestType 2) |

**المتبقي قبل الانتهاء:** من 2026-11-20 إلى 2027-10-19 = **333 يومًا**.
**ملاحظة `autoRenewPeriod`:** تظهر عادةً بعد تجديد تلقائي؛ التاريخ الفعلي للانتهاء هو المعتمد أعلاه. يُنصح بتأكيد «التجديد التلقائي» ووسيلة الدفع في لوحة Spaceship.

### 2.1 ما يلزم لنقل الدومين إلى Cloudflare
1. **إضافة الموقع (Zone)** في Cloudflare بالدومين.
2. **تغيير Name Servers** عند Spaceship إلى الزوج الذي يعطيه Cloudflare (شكل `xxx.ns.cloudflare.com`).
3. **DNSSEC:** إمّا حذف DS عند Spaceship قبل النقل (أبسط وأسرع)، أو إدخال DS الجديد الذي يوفّره Cloudflare بعد التفعيل. **إغفال هذه الخطوة = تعطّل الدومين عند الزوار.**
4. انتظار انتشار الـNS (دقائق إلى ساعات؛ قد تصل 24–48 ساعة).
5. التحقق: `dig NS sidawin8n.cfd` يعيد `*.ns.cloudflare.com` وحالة Zone = Active.

## 3) هل أستطيع تنفيذ إعدادات Cloudflare بحسابك؟

**نعم تقنيًا، وبضوابط أمنية — ولا حاجة لإعطائي كلمة مرور الحساب.**

### الطريقة الموصى بها: API Token مُقيَّد
- أنشئ Token من Cloudflare Dashboard بصلاحيتين فقط:
  - `Zone → DNS → Edit` (للنطاق `sidawin8n.cfd` فقط)
  - `Account → Cloudflare Tunnel → Edit`
- أُخزّنه **خارج المستودع** في `%APPDATA%\AiRemote-Server\tunnel\` (غير متتبَّع في Git)، وأستخدمه في أوامر `cloudflared`/API.
- **لا تُرسل كلمة مرور الحساب في المحادثة.** بعد انتهاء الإعداد: أطلب تدوير الـToken (Revoke + إنشاء جديد) أو أتوقف عن استخدامه.

### ما أستطيع فعله بالـToken
- إنشاء نفق مسمّى (Named Tunnel) وإصدار Token تشغيل له.
- إنشاء سجل DNS (CNAME إلى `<tunnel-id>.cfd...cloudflare`).
- ضبط ingress/الخدمة الأصلية (https://localhost:3001 مع `noTLSVerify`).
- تثبيت cloudflared كخدمة Windows، وتشغيله، وقراءة الحالة والسجلات.
- إجراء اختبارات الاتصال والقياس.

### ما يبقى عليك (لا يمكن لأحد غيرك)
- **تسجيل الدخول إلى Spaceship** لتغيير الـNS (أو إعطائي وصولًا — غير موصى به).
- **إضافة الدومين إلى Cloudflare** والتحقق من الملكية (إن طُلب).
- **قرار اسم المضيف** النهائي (مثل `remote.sidawin8n.cfd`).
- **الموافقة على اختبار من شبكة خارجية** (TECNO على LTE) — ممنوع حاليًا بلا إذن لحظي.

> ملاحظة: النفق يعمل حتى لو بقي الدومين عند Spaceship **فقط** عبر quick tunnel المؤقت — وهو غير مقبول للإنتاج.

## 4) التصميم الفني للنفق (إنتاجي)

### 4.1 الشكل
- **Named Tunnel** + **Token تشغيل** (`cloudflared tunnel run --token …`) ⇒ إعدادات ingress تُدار من لوحة Cloudflare (Remote-managed) ⇒ لا ملفات سرّية على القرص.
- **خدمة Windows** (`cloudflared service install`) ⇒ يبدأ مع الإقلاع ويُعاد تشغيله تلقائيًا.
- اسم مضيف واحد: `remote.sidawin8n.cfd` → `https://localhost:3001`.

### 4.2 مشكلة TLS الأصلية (حرجة)
السيرفر يقدّم TLS على 3001. خيارَان:
| الخيار | الوصف | التقييم |
|---|---|---|
| **أ** `originRequest.noTLSVerify: true` | cloudflared يتحدث HTTPS للأصل مع تجاهل شهادة ذاتية | أسرع، لكن يتطلب ثقة بالشبكة المحلية |
| **ب** مستمع HTTP داخلي مخصص (مثلاً 127.0.0.1:3002) للنفق فقط | Cloudflare تُنهي TLS، والأصل HTTP داخلي | **أنظف وأكثر أمانًا** — يوصى به عند التطوير |

### 4.3 ما يكسبه التطبيق من النفق
- **يسقط شرط `AGENT_CA_CERT`** (شهادة Cloudflare عامة) ⇒ تبسيط نشر الوكلاء.
- `serverUrl = wss://remote.sidawin8n.cfd` لجميع الأجهزة.
- WebSocket مدعوم عبر Cloudflare؛ **الوكيل يرسل heartbeat كل 10 ث** والمشاهد ping كل 3 ث ⇒ لا قطع خمول.
- يبقى قيد `RELAY_SESSION_KBPS=2048` سقفًا للجلسة حتى يُرفع.

### 4.4 قيود يجب إدارتها
- Cloudflare ليست شبكة بث فيديو؛ لا تُبنى عليها وسائط CRD.
- سقف الرفع في خطّك هو سقف الجودة للخارج.
- أي انقطاع في Cloudflare = انقطاع الوصول العام (يبقى LAN).

## 5) بوابة PoC — تُقاس قبل أي تطوير

| القياس | الحد المطلوب |
|---|---|
| `/health` من شبكة خارجية | 200 · TLS صالح بلا استثناء |
| اتصال وكيل `wss` | < 2 ث · واستقرار 30 دقيقة بلا انقطاع |
| إعادة تشغيل النفق | عودة الوكيل < 60 ث |
| p95 RTT للوحة عبر WAN | < 150 ms على شبكة جيدة |
| بث شاشة | 1080p ≥ 8 fps أو 720p ≥ 15 fps |
| ملف 10MB | زمن وthroughput مقيسان (رفع/تنزيل) |
| سجل الأخطاء | 0 أخطاء TLS/WS خلال الاختبار |

**شرط أساسي:** الاختبار من **شبكة خارجية حقيقية**، لا من نفس الـLAN.

## 6) خارطة الطريق إلى مستوى Chrome Remote Desktop

| المرحلة | العمل | الناتج |
|---|---|---|
| **0** | نقل الدومين + Zone على Cloudflare | أساس الوصول الدائم |
| **1** | نفق مسمّى + خدمة + بوابة PoC أعلاه | وصول عام موثوق ومقيس |
| **2** | تضمين النفق في التطبيق (إعدادات/حالة/QR/تخزين آمن/إعادة تشغيل) | «وصول عن بُعد» بضغطة |
| **3** | TURN (coturn) + WebRTC media (VP8/H264) + DataChannel + fallback relay | زمن وجودة بمستوى CRD |
| **4** | تحسينات: تكيّف معدل، FEC، أدوات قياس، تسجيل جلسات | إنتاجية |

**تقدير:** 1 أسبوع للـPoC · 1–2 أسبوع للتضمين · 3–6 أسابيع لمسار الوسائط (يعتمد على نطاق CRD المطلوب).

## 7) الأمان

- نفق عام = سطح هجوم عام: ألزم 2FA على الحساب، وراقب `rate-limit` (مفعّل)، وفكّر في Cloudflare Access للوحة.
- رموز الأجهزة (`x-device-token`) وJWT موجودة؛ لا تضع أسرارًا في المستودع.
- تدوير API Token بعد الإعداد، وعدم مشاركته في محادثة.
- سجل تدقيق الجلسات موجود (`audit_log`) — فعّله في المراقبة.
- DNSSEC: عند النقل، إمّا حذف DS أو إدخال DS الجديد — وإلا تعطّل النطاق.

## 9) ملحق — حقائق مقيسة من الجلسات (مرجع)

- **P6 (بث المالك):** 10د6ث · 21/21 · **0/21 تشويش** · 1920×1080 · bad=0.
- **Relay:** `RELAY_MAX_SESSIONS=20` · `RELAY_OFFER_TTL_MS=60s` · **`RELAY_SESSION_KBPS=2048`** · قنوات `screen,control,files,chat`.
- **WebRTC M1:** `canvas.captureStream(30)` + `addTransceiver(sendonly, maxBitrate 4Mbps)` لكن **`iceServers: []`** ⇒ host candidates فقط ⇒ لا يعبر NAT.
- **النفق الحالي:** `cloudflared tunnel --url http://localhost:3001` (quick tunnel مؤقت) — لا يصلح إنتاجيًا.
- **الشهادة:** شهادة ذاتية على 3001؛ الوكلاء يحتاجون `AGENT_CA_CERT` (يسقط عبر النفق).
- **الاتصال عبر WAN اليوم:** غير مُهيَّأ (P5 «مسدود» لغياب مسار عام، لا لغياب قدرة).
- **وكيلا WIN10/WIN11:** على شيفرة أقدم؛ طلبات `view/files` تُرفض `password_required` حتى تحديثهما (جارٍ العمل عليه).
