## 1. ما نُفِّذ

| الطبقة | التفصيل |
|---|---|
| آلة الحالة | `requested → accepted → active → closed`، و`denied` / `expired`؛ كل انتقال عبر دالّة واحدة (`relayDecide` / `relayCloseSession`) |
| البيانات | جدول `session_tokens` (بصمة الرمز، الانتهاء، الاستهلاك) + صف في `sessions` عند القبول + تدقيق `session_*` |
| الطلب | `POST /api/relay/request` — يفحص القدرة **قبل** أي إشعار، ثم يتحقق من اتصال الهدف، ثم التعارض، ثم السعة |
| العرض | `session:offer` إلى الوكيل الهدف فقط، مع اسم الطالب وجهازه ونوع الوصول والمهلة |
| القرار | `session:accept` / `session:deny` من مقبس الوكيل الهدف، أو `POST /api/relay/:id/decision` لمالك الجهاز |
| الرمز | 64 hex، بصمته SHA-256 في القاعدة، صلاحية 90s، يُستهلك مرة لكل طرف، ويُرفض من أي جهاز ثالث |
| الربط | `relay:hello` ثم `session:ready` مع `peerDeviceId` و`peerOnline` |
| التمرير | `relay:data` بأربع قنوات (`screen`/`control`/`files`/`chat`)، ثنائي الاتجاه، مع عدّ بايت |
| الحارس | سقف `RELAY_SESSION_KBPS` لكل جلسة في نافذة ثانية + `session:throttled` مرة/ثانية |
| السعة | 20 جلسة افتراضياً، رفض صريح `503 relay_capacity` + تدقيق |
| التعارض | جلسة واحدة لكل جهاز، `409 session_conflict` (منع لا انتظار) |
| الانقطاع | إغلاق المقبس يغلق جلسات الجهاز بسبب `network` ويبلّغ الطرف الآخر ويُنهي صف `sessions` بالمدة |
| المراقبة | `GET /api/relay/sessions`، `GET /api/relay/:id`، بثّ `session:state` إلى اللوحة |
| الإغلاق | `POST /api/relay/:id/close` و`session:close` من أي طرف مع سبب |

**مسار الصلاحية قبل الإشعار (مُختبَر):** مستخدم بلا قدرة على الجهاز يحصل على `403 session_policy_denied`، والوكيل الهدف **لا يستلم أي `session:offer`** — العداد لا يتغيّر.

## 3. قرارات هندسية

| القرار | السبب |
|---|---|
| جلسات R4 في الذاكرة + صف دائم في `sessions` | الحالة اللحظية سريعة التغيّر؛ التدقيق والمدة يكفيهما القاعدة. إعادة التشغيل تُسقط الجلسات (معلن) |
| مساحة أسماء `/api/relay/*` بدل `/api/sessions/*` | `/api/sessions` و`/api/sessions/:id` كانتا مستخدمتين لسجلّات الجلسات القديمة — التعارض كان يمنع الإقلاع (اكتُشف بالاختبار) |
| الرمز يُستهلك مرة لكل طرف بدل مرة واحدة مطلقة | الخطة تطلب رمزاً واحداً مربوطاً بالطرفين؛ الاستهلاك لكل طرف يفي بالأمن بلا رمزين |
| تمرير الحزم بهوية المقبس بعد الربط، لا بالرمز | يمنع إعادة استخدام رمز مسرّب من جهاز ثالث حتى لو عرفه |
| إغلاق فوري عند انقطاع الشبكة (`network`) بدل تعليق 15 ثانية | لا جلسة معلّقة (بوابة الخطة)؛ إعادة الربط الشفافة تحتاج حالة `suspended` وهي بند لاحق |
| حارس النطاق على حجم الرسالة في نافذة ثانية | أبسط تطبيق يقيس فعلياً ويمنع استنزاف السيرفر بجلسة واحدة |
| التعارض = منع، لا انتظار ولا استبدال | أوضح سلوك للمستخدم وأسهل اختباراً؛ الاستبدال يحتاج واجهة قرار |

## 4. ما لم يُنفَّذ (بصراحة، ولا يُدَّعى)

1. **واجهة «اتصال بجهاز»** في وكيل Windows/Android وشاشة الموافقة على الطرف الهدف — ضمن R6. البروتوكول والمسارات جاهزة لها.
2. **إعادة الاتصال خلال 15 ثانية بلا إغلاق** — السيرفر يغلق الآن. تحتاج حالة `suspended` ومؤقّت سماح.
3. **بوابة الخطة «20 جلسة متزامنة بلا تدهور يتجاوز 15%»** — لم تُقس؛ القياس يحتاج 40 مقبساً وحمّالة بايت حقيقية على جهاز واحد، وهو بند قياس مستقل. المُثبت الآن: السقف يرفض بوضوح عند 20 (اختُبر عند 2).
4. **WebRTC/TURN** — مؤجّل بقرار المالك.
5. **استمرارية الجلسات عبر إعادة تشغيل السيرفر** — غير موجودة.
