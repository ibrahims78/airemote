## 2. السبب الجذري (من الكود، لا تخمين)

```js
// capture.html — captureFrame()
if (d && d.none && (Date.now() - lastFullAt) < 1500) {
  armTimer(1000 / currentFps); return        // (أ) ساكن: لا تُرسل شيئاً… لمدة 1.5 ثانية فقط
}
const sinceFull = Date.now() - lastFullAt
if (d && !d.none && region < 55% && sinceFull < 2000) {
  mode = 'delta'                             // (ب) دلتا مسموحة فقط خلال 2 ثانية من آخر إطار كامل
}
```

**التسلسل الفعلي على سطح مكتب ساكن:**

1. عند t=0 يُرسل إطار كامل (أول إطار أو إطار دوري).
2. الشاشة لا تتغيّر → الشرط (أ) يمنع الإرسال… لكنه **ينتهي عند 1500ms**.
3. بعد 1500ms يصبح `d.none` صحيحاً لكن الشرط لم يعد ينطبق → يسقط الكود إلى الإرسال **كاملاً**.
4. الشرط (ب) لا يُنقذ الموقف لأن `d.none` صحيح (لا منطقة متغيّرة تُرسل كدلتا).

**النتيجة:** كل إطار ساكن إطار كامل بحجم ~240KB، والفاصل 1538ms ≈ 1500ms المضبوطة في الكود.
هذا يفسّر الأرقام الثلاثة معاً: `fullFrameRatio = 1.0`، و`avgFrameKB = 239.7`، و`p50 = 1538ms`.

**سبب وجود المنطق:** لا توجد آلية «طلب إطار مفتاحي» في البروتوكول (فُحص: صفر مراجع لـ`force_keyframe` في السيرفر والوكيل). فالإطار الكامل الدوري هو الطريقة الوحيدة التي يحصل بها الملتحق الجديد على صورة كاملة — لكن الفاصل المختار (1.5–2 ثانية) مكلف جداً.

## 3. الإصلاح المقترح (ثلاث قطع مترابطة)

### أ) بروتوكول: طلب إطار مفتاحي عند الالتحاق

| الطبقة | التغيير |
|---|---|
| السيرفر (`server.js`) | عند التحاق مشاهد جديد بجلسة نشطة: `sendJson(agentWs, { type:'server:force_keyframe', payload:{ sessionId } })` |
| الوكيل (`main.js`) | `case 'server:force_keyframe': win.webContents.send('force-keyframe')` |
| الملتَقط (`capture.html`) | `ipcRenderer.on('force-keyframe', () => { forceFull = true })` ويُستهلك في أول لقطة |

**الأثر:** الملتحق يحصل على صورة كاملة فوراً بدل انتظار الإطار الدوري.

### ب) منطق الإطارات

```js
const FULL_REFRESH_MS = 15000          // أمان فقط: إطار كامل كل 15 ثانية كحد أقصى
if (forceFull) { forceFull = false; mode = 'full' }
else if (d && !d.none && region < 55% && (Date.now() - lastFullAt) < FULL_REFRESH_MS) mode = 'delta'
else if (d && d.none && (Date.now() - lastFullAt) < FULL_REFRESH_MS) { /* لا تُرسل */ }
else mode = 'full'
```

**الأثر المتوقع:** الساكن يرسل **صفر إطارات** عند عدم التغيّر (لا 240KB كل 1.5s)، ودلتا صغيرة عند حركة المؤشر، وإطاراً كاملاً واحداً كل 15 ثانية كأمان.

### ج) تعديل هدف R1 المعلن (تصحيح ذاتي موثّق)

هدف «ساكن ≥ 8 fps» في الخطة غير صحيح منطقياً: سطح المكتب الذي لا يتغيّر **لا يجب** أن يرسل إطارات. الهدف الصحيح:

| المؤشر | الهدف المصحّح |
|---|---|
| نطاق الساكن | **≤ 80 KB/s** (بدل 167.8) |
| متوسط الإطار عند وجود تغيّر | **≤ 25 KB** (بدل 239.7) |
| نسبة الإطارات الكاملة في الساكن | **≤ 0.10** (بدل 1.00) |
| نطاق النشط | **≤ 350 KB/s** |
| نطاق/إطار النشط | **≤ 30 KB** (محقَّق أصلاً: 23.7) |

يُسجَّل هذا التصحيح في الخطة §R1 وفي `PROJECT_STATE.md` — لا تغيير هدف بصمت.

## 4. خطة التحقق (بعد التطبيق)

1. بناء حزمة الوكيل وتثبيتها على WIN10 (أو تشغيل الوكيل من المصدر على الـVM).
2. `node scripts/perf/measure.cjs --device WIN10 --mode idle --seconds 10 --runs 3` → ساكن.
3. `--mode active` مع تحريك المؤشر في الضيف → نشط.
4. بوابة: `--baseline docs/perf-baseline.json` يجب أن تمرّ بالنسب الجديدة، ثم يُحدَّث خط الأساس بعد التحقق.
5. اختبارات `e2e-screen-join` و`e2e-screen-control` يجب أن تبقى خضراء (الالتحاق المتأخر هو الحالة الحساسة).

**خطر يجب مراقبته:** إن أُرسل الملتحق الجديد قبل وصول الإطار المفتاحي المطلوب، سيرى صورة قديمة حتى 15 ثانية. لذلك القطعة (أ) **شرط** لتطبيق (ب)، وليست تحسيناً اختيارياً.

## 5. لماذا لم يُطبَّق بعد

التغيير يمسّ `capture.html` داخل حزمة الوكيل المثبّتة (`app.asar`). تطبيقه بلا إعادة بناء وتثبيت على الـVM يعني قياساً على كود قديم — أي دليل كاذب. الخطوة التالية عملية: بناء `releases/agent-windows` ثم تثبيت ثم قياس.
