# TC-024 — viewer performance (2026-11-04)

Measured through the same CDP harness (Chrome, 1600x900, WIN10-VM stream at the default preset):

- TIME_TO_FIRST_FRAME_MS = 110
- FPS samples over 12s     = 3, 2, 1, 1, 1, 1   (avg 1.5, min 1, max 3)
- Rate samples             = 335.6KB/s, 223.2KB/s, 111.4KB/s then steady 111.4KB/s
- HEAP_MB                  = 10.9

Reading of the numbers (honest):
- The 110ms start is the real win: the viewer paints the first frame before the stream is even
  steady, which is what TC-024 cares about.
- 1–3 fps is NOT a performance verdict. The VM desktop was static during the measurement and the
  stream is change-driven, so a static screen legitimately produces 1–3 fps at ~111KB/s. Earlier
  project baselines recorded the same shape (static ~0.55Mbps, ~2.8fps).
- A meaningful fps ceiling needs a moving screen (window drag / video) — that was not run here.

Verdict: PASS for start latency; the fps figure is informational, not a pass/fail on throughput.
Still open for TC-024: fps/bitrate under motion, and the 6-tile preview ceiling (not reachable
with only 3 streamable devices — see ui/preview-wall-measure.txt).
