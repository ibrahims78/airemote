### Deviation found on WIN10
Installed asar matched the host (ASAR_SHA=bb71469e..., 664761 bytes, written 15:33:43),
but the running agent stayed on the old build:
  AGENT pid=5416 start=12:49:16
  AGENT pid=6480 start=12:49:17
  AGENT pid=6652 start=12:49:17
  AGENT pid=4564 start=15:25:01
  WORKER capture-gdi-worker-4751af4e start=12:49:20
Root cause: those processes came from scheduled task "\AiRemote Agent (Elevated)" (RL HIGHEST).
The lab shell in the guest runs with a filtered token:
  GROUPS_IL = Mandatory Label\Medium Mandatory Level (S-1-16-8192)
  IS_ADMIN = False
  net session = System error 5
  schtasks /Create ... = ERROR: Access is denied.
So a forced stop of the elevated processes is impossible from the filtered token;
restart-clean-3130.ps1 re-spawned the same stale worker instead.

### Remediation
vmrun -T ws reset Win10_Pro_Custom.vmx (exit 0) -> logon task relaunched the agent from the new asar.

## Lesson (new)
An elevated agent cannot be replaced from a filtered-token guest shell: the asar on disk
changes but the running processes survive. Reboot the guest (or end the task from an elevated
context) — do not trust SIZE_MATCH as proof that the new build is live. Verify process start
times against the swap time.
